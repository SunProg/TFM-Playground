# Realistic SCM multiregime results at 5,000 steps

This report consolidates the completed CREATE Slurm runs on the realistic
two-regime SCM profile. Each configuration used 128 support examples, 256
query examples, four observed task features plus a regime cue, two latent
regimes with probability 0.65/0.35, cue separation 1.5, two nonlinear
mechanism layers of width 12, and 5% label noise. Final test metrics use 128
episodes. Checkpoints were selected by minimum validation cross-entropy.

## Results

| Model / head | Seed 11 | Seed 12 | Mean accuracy | Mean CE |
|---|---:|---:|---:|---:|
| Table-slot `decoder_baseline` | 81.46% | 80.60% | **81.03%** | **0.4345** |
| Plain NanoTabPFN | 75.77% | 75.31% | **75.54%** | **0.5054** |
| Table-slot `blind_similarity` | 67.47% | 58.12% | **62.80%** | **0.6380** |
| Table-slot Mufasa | 74.32% | 50.41% | 62.37% | 0.6078 |
| Table-slot `decoder_alpha` | 49.81% | 50.34% | 50.07% | 0.6932 |
| Table-slot `blind_decoder` | 50.41% | 50.41% | 50.41% | 0.6931 |
| Table-slot backbone | 50.41% | 50.41% | 50.41% | 0.6931 |

The baseline table-slot decoder is the strongest result, exceeding the plain
NanoTabPFN reference by 5.49 percentage points. `blind_similarity` learns a
weaker signal. Alpha routing and the blind decoder remain at chance. Mufasa
is highly seed-sensitive: one seed reaches 74.32%, while the other remains at
chance.

Support-label shuffling gives approximately chance accuracy for every model:
49.9% for the table-slot baseline, 49.9% for NanoTabPFN, 50.3% for Mufasa,
and roughly 50% for the other heads. This is consistent with the successful
runs using the in-context support labels rather than a fixed label prior.

The 5,000-step NanoTabPFN result is substantially better than the earlier
1,000-step mean of 53.69%, showing that the shorter budget was insufficient
for this profile. The table-slot baseline also improves over its earlier
1,000-step mean of 73.35%.

## Capacity-control experiment

To test whether the earlier gap was caused only by the small model, I added
architecture controls to the SCM trainers and trained a much larger plain
NanoTabPFN and table-slot decoder baseline on the same prior, episode stream,
optimizer, and 5,000-step budget. The original backbone has
`embedding=32`, `heads=4`, `MLP=64`, and `layers=2` (28,034 parameters). The
large backbone has `embedding=192`, `heads=6`, `MLP=768`, and `layers=6`
(3,711,362 parameters, about 132x larger).

| Model | Selected steps (seeds 11 / 12) | Overall acc / CE / AUC | Majority `z=1` acc / CE / AUC | Minority `z=0` acc / CE / AUC |
|---|---:|---:|---:|---:|
| Large plain NanoTabPFN | 3,600 / 5,000 | 50.41% / 0.6931 / 0.4998 | 50.27% / 0.6932 / 0.4997 | 50.64% / 0.6931 / 0.5002 |
| Large table-slot `decoder_baseline` | 5,000 / 1,600 | 50.50% / 0.6931 / 0.5019 | 50.41% / 0.6931 / 0.5010 | 50.65% / 0.6931 / 0.5034 |

Support-label shuffling produced the same near-chance metrics for the large
models. The large runs therefore did not recover the SCM signal under the
small-model optimization recipe: increasing capacity alone was insufficient.
Because both large models also failed to learn at all, this is not yet a pure
capacity conclusion; optimization scale (learning rate and warmup) is a
remaining confound. The follow-up should use the large model's intended lower
learning rate before ruling out capacity.

The capacity checkpoints are in
`results/scm_nanotabpfn_realistic_large_5000_slurm/37090255/` and
`results/scm_table_slot_head_realistic_large_5000_slurm/37090256/`. The
regime-stratified raw evaluation is
`results/scm_realistic_5000_capacity_regime_stratified.json`. The training
arrays were Slurm jobs `37090255` (plain) and `37090256` (table-slot), and the
stratified evaluation was job `37090421`.

## Capacity-aware optimization follow-up

The large plain NanoTabPFN was retrained with the same architecture and prior,
but with learning rate `1e-4` instead of the small-model `1e-3` recipe. This
separates model capacity from the optimization setting that caused the matched
large run to remain at chance.

| Model | Selected steps (seeds 11 / 12) | Overall acc / CE / AUC | Majority `z=1` acc / CE / AUC | Minority `z=0` acc / CE / AUC |
|---|---:|---:|---:|---:|
| Large plain NanoTabPFN, lr `1e-4` | 5,000 / 3,800 | 66.50% / 0.5509 / 0.6997 | 66.98% / 0.5432 / 0.7011 | 65.58% / 0.5649 / 0.6984 |

The result is strongly seed-sensitive. Seed 11 reaches 82.59% overall accuracy,
0.4087 CE, and 0.8948 AUC, with 80.53% accuracy on the minority regime;
seed 12 stays at 50.41% accuracy, 0.6931 CE, and 0.5046 AUC. Thus capacity
can support the SCM signal when the optimization is retuned, but capacity alone
does not guarantee learning or explain the table-slot advantage. The next
capacity comparison should use matched learning-rate sweeps and more seeds.

The lower-rate checkpoints are in
`results/scm_nanotabpfn_realistic_large_lr1e4_5000_slurm/37090428/`, and the
regime-stratified evaluation is
`results/scm_realistic_5000_capacity_lr1e4_regime_stratified.json`. Training
was Slurm array `37090428`; evaluation was job `37090483`.

## Capacity-control with the prior-family optimizer

The previous capacity comparison used a fixed `1e-3` learning rate and left
the large models at chance. I reran both large architectures with the optimizer
used by the plain/mixed/curriculum prior-family trials: AdamW peak learning
rate `1e-4`, 2,000-step linear warmup, cosine decay to `1e-6`, weight decay
`0.01`, and gradient clipping at `1.0`.

| Model | Selected steps (seeds 11 / 12) | Overall acc / CE | Shuffled-support acc / CE |
|---|---:|---:|---:|
| Large plain NanoTabPFN | 5,000 / 4,600 | **82.46% / 0.4095** | 49.56% / 0.7867 |
| Large table-slot `decoder_baseline` | 5,000 / 4,800 | **82.50% / 0.4101** | 49.71% / 0.7926 |

With the matched prior-family schedule, both large models learn reliably and
are essentially tied on overall accuracy. This means the earlier failure was
caused by the optimizer mismatch, not insufficient capacity.

Regime-stratified evaluation job `37093031` evaluated the validation-selected

## Official TabPFN: fixed weights versus per-episode fine-tuning

Both conditions use the same realistic SCM profile (128 support rows and 256
query rows). **Fixed weights** means the released TabPFN checkpoint receives
the support set through its usual `fit` interface, but its parameters are not
updated. **Per-episode fine-tuning** starts a fresh copy of that same released
checkpoint for every episode, updates it only from that episode's 128 support
rows, and then scores its 256 held-out query rows. It does not pretrain one
model across the 128 episodes.

The fine-tuning configuration was five epochs, learning rate `1e-5`, the
package scheduler, a 20% support-set validation split, early-stopping patience
2, and 2/2/8 estimators for fine-tuning/validation/final inference. Fixed
weights used eight estimators, softmax temperature 0.9, no probability
balancing, no averaging before softmax, and `fit_preprocessors` mode.

| Version | Condition | Overall acc / CE / AUC | Majority `z=1` acc / CE / AUC | Minority `z=0` acc / CE / AUC |
|---|---|---:|---:|---:|
| v2.2.1 | Fixed weights | 78.43% / 0.4824 / 0.8548 | 81.19% / 0.4472 / 0.8795 | 73.39% / 0.5470 / 0.8021 |
| v2.2.1 | Per-episode fine-tuning | **79.10% / 0.4711 / 0.8657** | 80.87% / 0.4464 / 0.8808 | **75.75% / 0.5171 / 0.8361** |
| v2.6 | Fixed weights | 76.18% / 0.5110 / 0.8320 | **79.71% / 0.4666 / 0.8659** | 69.65% / 0.5930 / 0.7590 |
| v2.6 | Per-episode fine-tuning | 76.24% / 0.5075 / 0.8371 | 78.84% / 0.4737 / 0.8624 | 71.27% / 0.5713 / 0.7821 |
| v3 | Fixed weights | 78.47% / 0.4809 / 0.8557 | **81.40% / 0.4419 / 0.8811** | 73.07% / 0.5529 / 0.8009 |
| v3 | Per-episode fine-tuning | 78.70% / 0.4823 / 0.8610 | 80.34% / 0.4560 / 0.8760 | 75.58% / 0.5318 / 0.8287 |

The current fixed-weight runs use deterministic namespace 3,000,000, while
the fine-tuning runs use namespace 4,000,000. Thus the following changes are
descriptive comparisons over equally sized draws from the same prior, **not
paired estimates on identical episodes**:

| Version | Overall change after fine-tuning | Majority `z=1` change | Minority `z=0` change |
|---|---:|---:|---:|
| v2.2.1 | +0.67 pp acc / −0.0113 CE / +0.0109 AUC | −0.32 pp / −0.0008 / +0.0013 | +2.36 pp / −0.0299 / +0.0340 |
| v2.6 | +0.06 pp acc / −0.0035 CE / +0.0051 AUC | −0.87 pp / +0.0071 / −0.0035 | +1.62 pp / −0.0217 / +0.0231 |
| v3 | +0.23 pp acc / +0.0014 CE / +0.0053 AUC | −1.06 pp / +0.0141 / −0.0051 | +2.51 pp / −0.0211 / +0.0278 |

Across all three versions, the descriptive pattern is a modest overall change
and a larger minority-regime gain, with a majority-regime accuracy decrease.
To remove episode-stream variation, I reran the fixed-weight checkpoints on
the same namespace-4,000,000 stream used by fine-tuning (job `37093550`).

| Version | Matched fixed weights: overall acc / CE / AUC | Majority `z=1` acc / CE / AUC | Minority `z=0` acc / CE / AUC |
|---|---:|---:|---:|
| v2.2.1 | 78.90% / 0.4718 / 0.8611 | 81.06% / 0.4429 / 0.8808 | 74.89% / 0.5256 / 0.8209 |
| v2.6 | 75.93% / 0.5090 / 0.8331 | 79.21% / 0.4688 / 0.8647 | 69.90% / 0.5835 / 0.7682 |
| v3 | 78.48% / 0.4754 / 0.8584 | 80.54% / 0.4453 / 0.8778 | 74.72% / 0.5311 / 0.8186 |

Against this matched reference, per-episode fine-tuning raises minority
accuracy by about 0.9--1.4 percentage points and minority AUC by about
0.01--0.02, while majority accuracy changes slightly downward. The overall
gain is small: about +0.2 pp for v2.2.1, +0.3 pp for v2.6, and +0.2 pp for v3.
The matched v3 fine-tune has higher overall CE than its fixed-weight reference,
so accuracy and AUC should be reported together rather than treating the
adaptation as a universal improvement.
